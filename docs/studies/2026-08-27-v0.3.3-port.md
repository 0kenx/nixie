## The two bugs the port itself found

### 1. Write-map faithfulness under co-equal indices (false `unsat`)

Upstream's `store_commutativity_without_distinctness_is_sat` control failed on
the fork: `(not (= (store (store a i x) j y) (store (store a j y) i x)))` is SAT
(take `i = j, x ≠ y`) and the fork answered **`unsat`**. Root pattern: a
store-chain write *map* `{i₁→v₁, …, iₖ→vₖ}` is a faithful model of its chain
only under pairwise-distinct indices — with co-equal symbolic indices the two
orderings keep different survivors at the shared index. Three layers shared the
blindness; all fixed:

- `check_array::store_chains_concretely_equal` (the syntactic storecomm fast
  path — the layer that produced the false verdict): "concretely equal" now
  additionally requires every chain's own index terms pairwise *provably*
  distinct (distinct literals); otherwise `None` → CDCL(T).
- `finite_disjunction_extensionality`: the flat value-disjunction lemma is
  emitted guarded by each chain's pairwise index distinctness; `is_complete`
  only when unguarded, so the fresh-witness clause is still minted for
  symbolic-index pairs.
- `build_read_over_write` flat SAME-implications (direct + aliased):
  order-aware guards (`row_same_guard`) — an inner write is visible only where
  the read index misses every outer write it could co-equal.

### 2. Clause-dedup memos survive `pop` (false `sat`, pre-existing on main)

The `define-fun-rec` port's `get_consequences` e2e test failed; reduction
removed `define-fun-rec` entirely and produced a 5-line QF_LIA repro that fails
on **pristine main**:

```text
(assert (= p (= x 5))) (assert (not p)) (push 1) (check-sat) (pop 1)
(assert (= x 5)) (check-sat)   ; must be unsat; main answers sat
```

Investigation path (recorded so it is not repeated): an initial "stale watch
lists in `oxiz_sat::Solver::pop`" theory was **disproved** — a standalone
`oxiz-sat` replay of the same clause/unit sequence answers correctly, and the
SAT cores of the working and failing checks turned out isomorphic. Clause-level
backtrace tracing (`OXIZ_SAT_TRACE=2` + `std::backtrace`) attributed the
missing constraints to the lazy check-time passes, whose dedup memos state the
false assumption in their own comments ("persists in the SAT core … never
removes base clauses" / "whose clauses survived (no retracting `pop`)"): a
clause emitted during a check that runs **inside a push scope** is retracted by
`sat.pop()` with the scope, the memo key survives, and the clause is never
re-emitted. Two instances fixed (`numeric_eq_split_pairs`,
`arith_const_axiom_pairs`); the class swept (`care_split_pairs` and
`arith_defined_terms` were already journalled). One process note: an
intermediate "fix doesn't work" observation was a **stale binary** — a
disk-full build failure left the previous executable in place; the memo fix
alone repairs every repro once the binary is genuinely rebuilt.

## Third session (2026-08-28, later): the three exposed bugs dug to the bottom

All three bugs the A1 trajectory change woke were root-caused with
entry-invariant traps and backtrace pinning, and the first two are FIXED and
landed (`5d5ba84`):

1. **Simplex pop/assignment staleness** - three cooperating holes: (a)
   `intern_row_cached` computes a new slack's value only when
   `assignment_current` is up, so a slack interned while the flag was down
   keeps its `zero()` default forever; (b) `pop` restores the pre-mutation
   assignment snapshot but only marked staleness when the vector GREW - at
   unchanged length the restored values do not satisfy the restored tableau,
   flag still up, and shape (a) can launder a wrong value into the scope
   snapshot as if consistent; (c) `pivot` and `on_nonbasic_bound_change`
   consumed the vector without honoring the flag, so
   `propagate_bounds`/`tighten_bounds` pivoted on stale values (release builds
   use them silently). Fix: pop marks stale on ANY mutated scope, both
   consumers re-derive when the flag is down. EUF's own pop/conflict
   machinery was verified correct by a micro-test (merge chain vs live diseq
   conflicts).
2. **Wrong datatype witness** - `decided_dt_equalities` read SAT-true `Eq`
   polarity as "equal", but recognisor/congruence axioms' consequents are
   free Booleans; one set true under an unproven premise chained
   `p = C(...) = C'(...) = q` and the repair declined on a pair it had to
   separate. Fix: the two directions read different authorities - disequality
   from the SAT commitment, equality from EUF congruence classes only.
   The pinned test is un-ignored and green.
3. **Gate re-derived interface equalities from cross-theory artifacts** - a
   purification definition `(= (f x) $p)` splits `f(x)`'s value (EUF side)
   from `$p`'s (arithmetic side); reading both back and comparing reports the
   mismatch the definition papers over, and every candidate of the
   `sum(k)=6` refinement loop hit it. Fix: conjunct-level assertion checking
   where an `Eq`/`Not(Eq)` conjunct is decided by its SAT-committed polarity
   (a contradicting commitment still refutes - the gate keeps its teeth).

**Still deferred, dependency now precise**: the A1 trichotomy + the gate's
negated-equality half. The trichotomy is what makes committed-false
equalities reach the LP as strict bounds (so the gate's second half stops
reporting collisions the fork repairs late), but its trajectory exposes a
FOURTH latent gap: **ite-guard conditional equalities never reach the
tableau** - the gate honestly reports `(=> (<= x 0) (= 0 ite_x))` evaluating
false (guard true in the LP, ite value != 0) on the recfun `sum(k)=6` goal,
and the blocking loop cannot recover within budget (starves to unknown).
Both code blocks are ready in this history; landing them is one fix away:
relay the ite-guard conditional eq to arith when its guard commits.

## Postscript: corpus-destruction incident and restoration

**What happened.** During the port, the worktree needed the untracked corpora;
three links (`satcomp2024`, `satcomp2025`, `satlib` → the primary tree) were
accidentally committed by a `git add -A` (a `.gitignore` entry with a trailing
slash — `/satcomp2024/` — ignores the *directory* but not a *symlink* of the
same name). Landing that commit on `main` made git check the symlink out over
the primary tree's real directory: **git clobbers ignored paths at checkout**,
so the real `satcomp2024/`, `satcomp2025/` and `satlib/` directories (the
curated GBDB-layout corpora) were destroyed. `smt-lib/` survived (its link was
one level down, inside the directory).

**Restored.** Every test-consumed corpus file (4 files, `oxiz-sat`'s
watch-position/elimination/shrink/ELS regressions) was re-fetched from the
Global Benchmark Database (`https://benchmark-database.de/file/<md5>?context=cnf`,
xz-compressed) and is **byte-identical** to the lost copy (md5 checked against
a value recorded earlier in the session). `cargo nextest -p oxiz-sat` is
870/870 again. `satcomp2025/main_easy_mid/6s167-opt.cnf` (one benchstore cell
input) was not re-fetched; the result store never re-runs existing cells.

**Not restorable from record.** The wider curated corpora (the 45/60-file
standing sets named by short name in the studies) were not recorded with their
sha/md5 prefixes anywhere in-tree. Rebuild them with the same one-line recipe
per file (`curl -sL "https://benchmark-database.de/file/<md5>?context=cnf" |
xz -d > satcomp2024/bench/<md5>-<name>.cnf`); the standing-table file names are
in `docs/studies/2026-08-satcomp-standing-gap.md`.

**Lesson (now also implied by the cleanup rules).** (1) Never let a symlink
into an index path where the target name is a gitignored *directory* — the
trailing-slash ignore does not cover it, and checkout will clobber the real
data. (2) `git add -A` in a worktree that had to synthesize corpus links is
how it got in; add paths explicitly. (3) The one reason this was recoverable
at all: the corpora are external and content-addressed (GBDB md5s in the file
names).
