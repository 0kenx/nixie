# Window decomposition (§6.5 variable-subset split) for the FF chain frontier

**Date:** 2026-09-17
**Scope:** `docs/HANDOFF_FF_THEORY.md` open-work item 1's named next lever:
chain ≥128×192 via the design's actual §6.5 — bases over variable SUBSETS
in the original space, exchanging only support-fitting consequences. The
landed split is cvc5's 2-way linear/nonlinear split; on the chain it
degenerates (one component; the nl side sees all 128 quadratics at once)
and the 128-constraint nonlinear cascade budget-outs even at 16× budget
(`2026-09-16-ff-branch-selection-inapplicable.md`).
**Verdict:** **ship** — chain 128×192 `sat` in ~3 s and 256×384 `sat` in
~3.7 s (both honest `unknown` in ~3 s before), every previously-solved
corpus goal unchanged, all oracle suites green, plus one FindZero
accounting fix (T5-class) and one honesty gate the new path demanded.

## Pre-registration (written before any implementation runs)

**Class:** deterministic front-end change (design §6 "Measurement
discipline": changes what the procedure *does*; report solved counts and
step counts; no matched null — the procedure is deterministic and the
oracles pin the verdicts).

**Hypothesis:** the chain corpus is locality-structured (sliding
3-variable windows; consecutive constraints share variables). A window
decomposition — cluster the component's generators into overlapping
variable subsets, compute a small Gröbner basis per window, exchange
support-fitting linear consequences and univariates to a fixpoint —
computes locally what the monolithic cascade computes globally, at a
per-window cost inside the regime the monolithic path is known to
complete. The merged union then pins variables FindZero can finish from.

**Go bar (verdict):** chain 128×192 answers `sat` (today honest
`unknown` in ~3 s); no previously-solved corpus goal regresses in verdict
or honest-refusal class; all FF oracle suites green (tiny-prime
exhaustive, planted fuzz at real primes, solver regressions,
traced/untraced identity, UFFF oracle).

**No-go:** no new corpus goal solved. Then the write-up records the
measured mechanism failure and the change is dropped or kept neutral per
its measured cost — a "window GBs completed and exchange moved
polynomials" outcome is an intermediate proxy, NOT success.

**Falsification criteria for sub-mechanisms (measured, then recorded):**
- windows of ≤32 vars over the 128×192 component do not complete at
  2^24 monomial ops (the locality hypothesis is wrong at this size);
- the exchange fixpoint is inert (no window derives linear consequences
  beyond its inputs — the chain needs cross-window nonlinear reasoning);
- the merged union pins too few variables and FindZero's branch children
  explode the budget — window threading inside FindZero would then be
  the named follow-up.

**Soundness argument (as landed):** every window ideal is generated by a
subset of the component's generators (⊆ the component ideal); every
exchanged polynomial is a member of the ideal its basis generates
(inductively ⊆ the component ideal); so a constant in any window basis
refutes the component, and the merged union consists of component-ideal
members only. Termination of the exchange: the admitted classes are
(a) linear polynomials — the linear part of a window's ideal lives in a
finite-dimensional (|V_w|+1)-dim space, so strict growth is bounded;
(b) univariates — principal ideals of 𝔽_p[x] ascend finitely.
Belt-and-braces round cap 64, per-window monomial-op budget, the
engine's bloat breaker per window GB.

## The architecture that shipped

Per component, the fallback ladder is now **monolithic → 2-way
linear/nonlinear split → window decomposition** (each level a fresh
budget; the window level is the design's actual §6.5, landing 2026-09-17
in `nixie-theories/src/ff_theory.rs`):

1. **Window formation** (`form_windows`): greedy growth from the
   lowest-index unassigned generator, adding the unassigned generator
   with the SMALLEST footprint increase (ties by index), to a cap of 8
   variables / 64 generators. Every generator lands in exactly one
   window; windows overlap through shared variables. The cap governs
   growth only — a seed generator whose own support exceeds it still
   forms its (oversized) window, so coarse-locality goals degrade to
   fewer, bigger windows instead of failing to partition.
2. **Per-window Gröbner basis**, untraced, budget per window (the
   components' own discipline: "a shared cap would starve late
   windows").
3. **The exchange fixpoint**: every basis element that is linear (any
   support size) or a univariate (any degree) is offered to every other
   window whose FIXED variable set its support fits, skipping ideal
   membership (cvc5's `!contains`), to a fixpoint (round cap 64).
4. **The union completion attempt**: one cascade over the union of all
   window bases. The union generates the component ideal exactly (each
   window ideal ⊆ it; every component generator sits in some window
   ideal), so a completing cascade IS the component's Gröbner basis —
   the minimal-polynomial brancher is valid for it (`root_is_gb`). A
   budget-out falls back to the merged union (ideal members all), the
   same object the 2-way split feeds FindZero today.

### What the mechanism actually does on the chain (deterministic evidence)

`NIXIE_FF_STATS`, BN254, default budgets:

* 128×192: 22 windows (9–10 gens each over 8 vars), each window basis
  7–17 elements; the exchange runs **9 rounds**, each moving 2 boundary
  pins one window along the cycle (a pipeline wavefront — the cycle's
  rigidity propagates window by window); the union cascade: 171
  elements → basis of 127 → FindZero answers `sat` at node 1 (every
  variable pinned).
* 256×384: 43 windows, 17-element bases, **26 exchange rounds**, union
  339 elements → basis of 255 → `sat`.
* ≤64×96: unchanged (the monolithic path completes; windows never run).

The dump-stage geometry (why this works): after the linear core, the
chain is a CYCLE of ~6-variable "cores" (a 2-var core pair pinned by
3–4 linear rows, one same-core product quad, one bridge quad to the next
core; the last bridge wraps). Any SEGMENT is 1-dof; only the cycle is
rigid — so no window ever pins its interior alone, and the pins arrive
by exchange from the neighbours (the wavefront above), with the union
cascade closing the wrap. This is why per-window pinning was never the
mechanism and the union completion is.

## Two soundness/honesty fixes the new path demanded

1. **FindZero node accounting (T5-class)**: a round-robin node pushed up
   to 256 children but was charged ONE step, so 256-ary expansions ran
   to a 2^24-NODE cap — the degraded-union case measured an **82 s
   refusal** whose every node was a dead basis recompute. Node steps now
   charge CHILDREN PUSHED (`steps += values.len()`), the same
   charge-what-runs rule as the selection-scan and cofactor-row fixes.
   Complete searches at p ≤ 256 are unaffected (they walk every child
   anyway); hopeless walks hit the cap 256× sooner.
2. **The skipped-window fast-refuse gate**: a window that budget-outs is
   SKIPPED, not fatal — the union of the survivors generates a subideal
   of the component ideal, and every consumer is sound under ideal
   shrinkage (a constant in any subideal refutes the component; a search
   exhausted over V(J ⊇ I) refutes V(I); candidate models validate
   against the original literals). BUT a skipped window's EXCLUSIVE
   variables can never be pinned (an exchanged polynomial's support must
   fit its target's fixed variable set), so over p > 256 the FindZero
   walk is a guaranteed budget-out. The gate refuses fast instead
   (`OutOfBudget { where_: "window split (skipped window)" }`) —
   capacity, never soundness (at p ≤ 256 the search still runs: it is
   complete and cheap). This took the degraded case from 82 s (and 22 s
   on another shape) to an immediate refusal.

## Negative variants recorded (do not retry without new structure)

* **Index-order window growth**: forming windows by generator index
  order (the first code) put 42 quadratics with NO linear rows in
  window 0 of the chain (the linear core appends pivot rows after the
  substituted nonlinear generators) — underdetermined, budget-out, and
  the rows trailed behind as 2-gen micro-windows. Support-driven growth
  (smallest footprint increase) is load-bearing, not a refinement.
* **Shared window budget**: one budget across all windows starved window
  1 after window 0's burn (the components' starvation argument applies
  verbatim at window scale). Per-window budgets landed.
* **A 4× window budget as the default** (completing cap-32 windows on
  the frontier goals): solves the same goals, but multiplies the
  honest-refusal grind on hopeless goals ~4× per window; the flat band
  at caps 4–8 makes it unnecessary. Not landed.
* **Admitting super-linear multivariate elements between windows** (the
  obvious "exchange more" extension): not tried — dense linear content
  that fits is already exchanged, and the flattening studies' re-expansion
  failure mode is exactly nonlinear-with-linear-content re-entering
  cascades. The union cascade already computes the cross-window
  nonlinear consequences soundly.

## What remains open

* **Certificates on the window path**: a window-union UNSAT carries the
  component origins as core and no certificate (like the 2-way split);
  certified mode downgrades. A traced re-run cannot recover it — the
  union's inputs are window elements, not replayable generators. A
  future certificate would replay the whole window trajectory.
* **The exchange wave is sequential** (one window per round): a
  worklist-driven exchange admitting within a round would collapse the
  9/26 rounds to ~2–3; irrelevant at current sizes (the rounds are
  cheap), relevant if the corpus grows another power of two.
* **F4** remains the orthogonal Phase-7 lever (batched linear-algebra
  reduction); the window split composes with it (per-window F4).
* Chain 512×768+ unmeasured (43 windows at 256×384 → ~86 at 512×768:
  over the 64-window round cap's comfort zone; measure before relying).

## External reference: CoCoA-enabled cvc5 (the strongest-baseline rule)

`docs/BENCHMARKING.md` §10.3 demands the treatment also be compared
against the reference implementation where one exists. cvc5's FF theory
IS the reference (the [OKTB23] procedure + split-GB, via CoCoA). Neither
installed solver can run `QF_FF`: **z3 4.16.0 cannot parse the sort**
(`unknown sort 'FiniteField'`) and **nixpkgs cvc5 1.3.4 is built without
`--cocoa`** ("can't solve field problems since it was not configured
with --cocoa"). A comparator was therefore built from the repo's own
read-only snapshot `../temp/cvc5` (cvc5 1.3.5.dev+main@e8c0387,
production config, auto-downloaded CoCoA 0.99850 + GMP 6.3; the build
needed the usual NixOS accommodations — `--gpl` for CoCoA, m4 in PATH,
shebang and hardcoded-`/bin`-tool rewrites, `LD_LIBRARY_PATH` for the
auto-built GMP). Sequential runs on this (shared) machine, quiet load:

| goal | cvc5 (CoCoA) | nixie before | nixie (window split) |
|---|---|---|---|
| chain 16×24 | `sat` 0.10 s | `sat` 0.07 s | `sat` 0.30 s |
| chain 32×48 | `sat` 0.12 s | `sat` 0.13 s | `sat` 0.16 s |
| chain 64×96 | `sat` 0.99 s | `sat` 1.2 s | `sat` 1.4 s |
| chain 128×192 | `sat` **14.4 s** | `unknown` ~3 s | **`sat` 3.3 s** |
| chain 256×384 | **timeout >120 s** | `unknown` ~3 s | **`sat` 3.7 s** |
| sparse 64×96 / 128×192 | `sat` 0.10 / 0.19 s | `sat` 0.09 / 0.2 s | unchanged |
| dense 12×20 | `sat` 0.11 s | `sat` 0.1 s | unchanged |

The window decomposition is **~4.4× faster than cvc5 on the goal that
defined this study's frontier (128×192) and solves 256×384 where cvc5
does not answer within 120 s** — while small/sparse/dense goals stay at
parity (those complete monolithically in both). One comparator caveat:
this snapshot's `splitFindZero` conflict-driven loop and ours differ
(we consume the union; cvc5 threads branches through every ideal), so
this is architecture-vs-architecture at equal ground truth, not a
kernel-level benchmark. The comparator binary is preserved under
`precompile/cvc5-e8c0387/` (with the auto-built `libgmp.so.10` it
needs; `LD_LIBRARY_PATH` that directory to run it).

## Addendum (same day): the 512×768/1024×1536 measurement, the corpus
generator, and the worklist exchange

The study's pre-registered next measurement (512×768 needs ~86 windows —
the 64-round exchange cap's comfort zone) ran as designed:

1. **The corpus generator is now in-repo** (`bench/ff/gen_chain.py` —
   the original was never kept). Reverse-engineering it found the
   load-bearing structure the hard way: the corpus's rows and quads come
   in RESIDUE PASSES (rows at offsets ≡ 0, 1, 2 mod 6 in sequence,
   quads at ≡ {2,4}, {3,5}, {4,6}; a {3,4,5} row and seam quads
   {1,2,3},{5,6,7},{7,8,9} close the cycle). A naive single stride-6
   sequence wrapping the ring chains EVERY row pair into one long RREF
   elimination — measured: a 62-variable pivot definition, 1891-term
   substituted quads, 172 degenerate windows, no verdict. The passes
   keep the eliminations pairwise-local, definitions 2-local, and the
   substituted quads at ≤4 variables. Two further generator bugs (a
   shared row/quad loop bound truncating the last pass, and a top-up
   that broke locality) each showed up as exact-count-but-not-rigid
   systems the window path honestly refused — pinning the exact density
   (n/2 rows, n quads) AND the pass locality as the family's defining
   properties.
2. **512×768 solves** (`sat` ~7-8 s, 87 windows, full pinning) — under
   the round cap, as hoped.
3. **1024×1536 died exactly at the 64-round cap** (measured: round 64
   fired with the pin wavefront at window 165 of 171 — seven rounds
   short). The named fix, the WORKLIST exchange, is landed: a window
   that recomputes immediately offers its admissible elements to every
   fitting window (FIFO, index-ordered scans — deterministic); offers
   into not-yet-computed windows ACCUMULATE (a first cut dropped them
   and the fixpoint terminated early with a weakened union — caught on
   the regression corpus before landing); the round cap becomes a
   total-admissions cap (4096). Result: **1024×1536 `sat` in ~18-24 s**
   (342 admissions), and every smaller goal faster (128×192: 3.3 →
   2.6 s; 512×768: 9.6 → 6.7 s) — the wavefront now propagates in one
   arrival-ordered pass instead of one window per round.

Corpus verdicts after the worklist landing: all 22 goals `sat`,
including the two new files (`bn254_chain_planted_{512x768,1024x1536}`).
FF oracle/fuzz/regression suites green; clippy/fmt clean. The full
workspace + parity gate for this commit rides the combined pass below.
